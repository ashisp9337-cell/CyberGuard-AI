# CYBERGUARD AI

AI-Powered Cyber Threat, Phishing & Digital Impersonation Detection and
Response System — a full-stack security platform: the existing React
frontend, wired to a real FastAPI backend with trained ML models, a
PostgreSQL-ready database, real authentication, and real (if limited)
threat intelligence.

## Architecture

```
Browser
  │
  ▼
React 19 + TypeScript + Vite  (frontend/, this repo root)
  │  HTTP (cookies, JSON, multipart)
  ▼
FastAPI backend (backend/)
  │
  ├── SQLAlchemy → PostgreSQL (the only database; schema managed by Alembic)
  ├── ML detectors (backend/app/detectors/, backend/app/ml/)
  │     • Phishing text: TF-IDF + Logistic Regression (trained, real)
  │     • Malicious URL: structural features + RandomForest (trained, real)
  │     • Account takeover / impersonation / cyber-threat: deterministic
  │       rule engines over the actual submitted input (no randomness)
  │     • Deepfake: real Pillow-based metadata analysis; clearly reports
  │       "model unavailable" rather than fabricating a verdict — see
  │       "Known limitations" below
  └── Threat intelligence (VirusTotal / URLhaus / AbuseIPDB via env keys;
        reports "unavailable" gracefully if a key isn't configured)
```

## Local setup (no Docker)

### 1. Backend

```bash
cd backend
python3 -m venv venv
source venv/bin/activate            # Windows: venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env                # set DATABASE_URL to your PostgreSQL database (see below)

# Apply migrations (creates all tables)
alembic upgrade head

# Train the ML models (writes app/ml/models/*.joblib — required before
# phishing/URL detection can use a trained model; the app still runs and
# falls back to rule-only detection without them, clearly labeled as such)
python -m app.ml.training.train_phishing
python -m app.ml.training.train_url_domain        # URL domain-name model
python -m app.ml.training.train_lookalike_domain   # needs: pip install dnstwist
python -m app.ml.training.train_domain_spoofing    # needs: pip install wordfreq

# Optional: seed demo data (demo@cyberguard.local / DemoPass123)
python -m app.db.seed

# Run tests (on a separate PostgreSQL database: <your db name>_test, created automatically)
pytest

# Start the API
uvicorn app.main:app --reload --port 8000
```

API docs: http://localhost:8000/docs

### 2. Frontend

```bash
npm install
cp .env.example .env
# .env defaults to VITE_API_BASE_URL=http://localhost:8000 — edit if your
# backend runs elsewhere.
npm run dev       # http://localhost:5173
```

Sign up for a real account (or log in with the seeded demo user above) and
every module/subtopic in the UI now calls the real backend.

## PostgreSQL setup

CyberGuard uses PostgreSQL only (the backend refuses to start with any other database). To run one:

```bash
# via Docker
docker run -d --name cyberguard-pg -e POSTGRES_USER=cyberguard \
  -e POSTGRES_PASSWORD=cyberguard -e POSTGRES_DB=cyberguard -p 5432:5432 postgres:16-alpine

# in backend/.env
DATABASE_URL=postgresql+psycopg2://cyberguard:cyberguard@localhost:5432/cyberguard
```

Then `alembic upgrade head` as above. Run it again after every update: the backend logs an error at
startup if the database schema is older than the code. The tests never touch this database: they use
`<name>_test` (e.g. `cyberguard_test`), which they create and wipe themselves (the name must end in `_test`).

## Running everything with Docker

```bash
docker compose up --build
```
Starts Postgres, the backend (migrating on boot), and the frontend dev
server. Train the ML models once via `docker compose exec backend python -m app.ml.training.train_phishing` (and `train_url_domain`, `train_lookalike_domain`, `train_domain_spoofing`) — model files aren't baked into the image so retraining/updating them doesn't require a rebuild.

## Environment variables

**Backend** (`backend/.env`, see `backend/.env.example`):
`DATABASE_URL`, `JWT_SECRET`, `COOKIE_SECURE`, `GOOGLE_CLIENT_ID`,
`GOOGLE_CLIENT_SECRET`, `TURNSTILE_SECRET_KEY`, `VIRUSTOTAL_API_KEY`,
`ABUSEIPDB_API_KEY`, `URLHAUS_API_KEY`, `CORS_ORIGINS`, `MAX_UPLOAD_MB`.

**Frontend** (`.env`, see `.env.example`):
`VITE_API_BASE_URL`, `VITE_AUTH_PROVIDER` (`backend` or `mock`),
`VITE_GOOGLE_CLIENT_ID`, `VITE_TURNSTILE_SITE_KEY`, `VITE_USE_MOCK_DATA`.

Anything prefixed `VITE_` is public/client-side by Vite's design — never
put a secret there. All non-`VITE_` backend values stay server-side only.

## ML model training

See `backend/app/ml/training/data/README.md` for dataset provenance and
how to swap in production-grade data. Both scripts print full metrics
(accuracy/precision/recall/F1/ROC-AUC + confusion matrix) — nothing here
claims "99.9% accuracy" without a real evaluation run.

## Deployment

**Frontend → Vercel.** `npm run build` produces `dist/`; `vercel.json`
handles SPA routing. Set `VITE_API_BASE_URL` to your deployed backend URL.

**Backend → Render / Railway / Fly.io (not Vercel serverless).** This
backend does file uploads, ML inference, and SQLAlchemy connection pooling
— a poor fit for stateless serverless functions with cold starts. Deploy it
as a long-running container (the provided `backend/Dockerfile` works as-is
on any of the above). Point `DATABASE_URL` at a managed Postgres instance
(Neon, Supabase, or the host's own Postgres add-on) and run
`alembic upgrade head` as a release/pre-deploy step.

**Database → Neon / Supabase / your host's managed Postgres.**

```
GitHub
  ├── Frontend → Vercel
  ├── Backend  → Render/Railway/Fly.io (Docker)
  └── Postgres → Neon/Supabase
```

## Security notes

- Passwords hashed with bcrypt; sessions are HTTP-only cookies (not
  localStorage), signed with `JWT_SECRET`.
- Google Sign-In is verified server-side against Google's public keys
  (`backend/app/core/security.py::verify_google_credential`) — the
  frontend's decoded profile is never trusted directly for the real
  backend path.
- Turnstile tokens are verified server-side against Cloudflare
  (`verify_turnstile`); without `TURNSTILE_SECRET_KEY` configured,
  verification is skipped in development and **fails closed** in
  production (`ENVIRONMENT=production`).
- Reset tokens are stored only as SHA-256 hashes, expire in 1 hour, and
  are single-use. `forgot-password` always returns the same response
  shape whether or not the email exists.
- CORS is restricted to `CORS_ORIGINS` — never `["*"]` with cookie auth.
- File uploads are extension-allowlisted, size-limited, stored under
  randomized filenames outside any web root, and never executed.
- Integration settings never persist client-supplied values containing
  `key`/`secret` in their field name.

## Known limitations (read before treating this as production-ready)

- **Deepfake/video/audio detection has no trained model.** This ships
  real static-metadata analysis for images (Pillow: EXIF, editing-software
  tags) and is explicit that this is a weak signal, not a verdict. Video
  and audio subtopics report "model unavailable" rather than fabricating
  a result. Plugging in a real trained model is a single documented
  integration point (`backend/app/detectors/deepfake.py::run_trained_model`).
- **ML models are trained on small public demo datasets** (5,574-message
  SMS spam corpus; a 5,000-URL sample), checked in so the pipeline runs
  out of the box. Real precision/recall on your actual traffic will
  differ — see `backend/app/ml/training/data/README.md` for where to get
  production-grade labeled data.
- **QR code decoding** requires `pyzbar` + the system `libzbar0` library
  (installed in the Docker image; install separately for bare-metal dev).
  Without it, QR phishing scans report the decoder as unavailable rather
  than fabricating a result.
- **Threat intelligence providers** (VirusTotal/AbuseIPDB/URLhaus) require
  your own API keys; without them the corresponding lookups report
  `"status": "unavailable"` rather than fake data.
- **PostgreSQL only.** `DATABASE_URL` must be a `postgresql+psycopg2://` URL; the
  backend stops with a clear message otherwise. Tables are created and upgraded
  only by Alembic (`alembic upgrade head`).
- **Live monitoring** streams via Server-Sent Events (`GET /api/monitoring/stream`,
  wrapped by `src/services/api/monitoringService.ts`), reflecting real
  `threat_events` rows as they're created by scans or `POST /api/events`.
  It's polling the database under the hood, not a message broker — fine
  for single-instance deployments; for multi-instance production you'd
  want Postgres LISTEN/NOTIFY or Redis pub/sub instead.
- **All primary pages are wired to the real backend**: Dashboard, Scan
  History, Threat Overview, Threat Intelligence, Live Monitoring, Reports,
  and Settings all call the FastAPI endpoints above instead of the local
  mock generators (`src/services/mock/mockData.ts` remains only as the
  `VITE_USE_MOCK_DATA=true` offline-demo fallback). Two exceptions, both
  clearly labeled in the UI rather than silently faked:
  - "Global Threat Activity" by region (Threat Intelligence page) has no
    backing geolocation/IP-intelligence pipeline — shown as labeled demo data.
  - The old "Network Activity" packet table (Live Monitoring page) had no
    real backend equivalent (no packet-capture pipeline) and was removed
    rather than left showing fabricated flows.
- Rate limiting is a basic in-memory `slowapi` limiter (200 req/min per
  IP) — fine for a single backend instance, not for multi-instance
  production (would need a shared store like Redis).
